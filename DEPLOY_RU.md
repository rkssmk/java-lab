# Развёртывание Java Lab на российском VPS

Этот документ предназначен для первого технического развёртывания. Он **не является юридическим разрешением на запуск**. До завершения `LEGAL_REVIEW_CHECKLIST.md` оставь регистрацию выключенной.

## 0. Что нужно заранее

- VPS в дата-центре РФ с Docker Engine и Docker Compose plugin.
- Домен, DNS A-запись на публичный IPv4 сервера (AAAA добавляй только если IPv6 полностью настроен).
- Открытые TCP-порты 80 и 443.
- Подтверждение от провайдера, где находятся диски, snapshots, резервные копии и технические журналы.
- Проверка договоров/поручений с хостинг-провайдером и другими обработчиками.

GitVerse Pages не запускает Java backend. Для облачных аккаунтов фронтенд и API должны быть на одном origin. Этот compose размещает `public/` и `/api/*` на одном домене через Caddy. GitVerse оставь для исходного кода; не используй его Pages как production-хостинг персональных данных без отдельной правовой оценки.

## 1. Подготовь DNS и сервер

1. Создай DNS A-запись `@` на IP VPS. Для `www` добавь отдельную запись или редирект, если нужен.
2. В firewall разреши входящий TCP 80 и 443. SSH разреши только с доверенных адресов по возможности.
3. Установи Docker Engine и Docker Compose plugin из официального репозитория ОС.
4. Войди на сервер по SSH и клонируй приватный/публичный репозиторий проекта:

```bash
git clone <URL_ТВОЕГО_GITVERSE_REPO> java-lab
cd java-lab
```

Не сохраняй пользовательские выгрузки, `.env`, пароли, SSH-ключи или recovery codes в Git.

## 2. Создай конфигурацию

```bash
cp .env.example .env
chmod 600 .env
```

Отредактируй `.env`:

- `DOMAIN` — реальный домен, указывающий на этот VPS.
- `DB_ADMIN_PASSWORD` — длинный уникальный пароль администратора PostgreSQL.
- `DB_PASSWORD` — другой длинный уникальный пароль непривилегированной роли приложения.
- `BACKUP_PASSPHRASE` — длинный случайный секрет для шифрования резервных копий.
- `BACKUP_HMAC_PASSPHRASE` — отдельный длинный случайный секрет для проверки целостности резервных копий.
- `APP_COOKIE_SECURE=true` оставить включённым.
- `APP_REGISTRATION_ENABLED=false` оставить выключенным.
- `APP_LEGAL_LAUNCH_APPROVED=false` оставить выключенным.
- `LEGAL_*` не заполнять выдуманными реквизитами.
- `RUNNER_ENABLED=false` оставить выключенным.

Для создания четырёх случайных секретов на сервере:

```bash
openssl rand -base64 48
openssl rand -base64 48
openssl rand -base64 48
openssl rand -base64 48
```

Используй четыре разных результата: пароль администратора БД, пароль роли приложения, passphrase шифрования backup и HMAC secret. Храни пароль БД и passphrase в секретном хранилище/защищённом менеджере, не в Git.

## 3. Запусти стек в режиме закрытой регистрации

```bash
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 backend
```

Caddy попробует получить TLS-сертификат для `DOMAIN`. DNS должен уже указывать на сервер, а порты 80/443 быть доступны извне.

Проверки:

```bash
curl -fsS https://$DOMAIN/api/health
curl -fsS https://$DOMAIN/api/meta/public
```

`/api/health` должен вернуть `status=ok`. В `/api/meta/public` регистрация должна оставаться `false`. Открой главную страницу: интерфейс должен загрузиться, а окно аккаунта — сообщать, что регистрация отключена до выполнения процедур оператора.

## 4. Сохранность базы

Резервная копия:

```bash
chmod +x deploy/backup.sh deploy/restore.sh
./deploy/backup.sh
```

Скрипт создаёт зашифрованный dump и отдельный HMAC-файл с независимым секретом. Перед восстановлением `deploy/restore.sh` проверяет HMAC и требует явного подтверждения `RESTORE`; восстанавливай сначала в пустую тестовую БД. Скрипт не удаляет существующие таблицы автоматически. Локальные копии хранятся 7 дней. Это не заменяет проверенную off-site копию: отдельное резервное хранилище также должно быть в допустимом регионе, с контролируемым доступом и отдельным ключом. Проверь восстановление на отдельной тестовой базе до появления настоящих пользователей.

Не добавляй каталог `backups/` в Git. В текущей поставке backup сохраняется на том же VPS; отказ всего сервера/диска может привести к потере и базы, и её локальных копий.

## 5. Перенос старого прогресса

Домен GitVerse Pages и новый домен VPS — разные browser origins, поэтому `localStorage` автоматически не переносится.

1. Открой старый Java Lab на GitVerse Pages.
2. Используй экспорт прогресса в JSON.
3. Открой новый домен VPS и импортируй файл через кнопку импорта.
4. После завершения юридических и технических процедур пользователь сможет создать аккаунт; при первом входе сайт предложит загрузить локальный прогресс в личное облако.

Не присылай резервные копии прогресса посторонним: в заметках и черновиках может быть личный текст.

## 6. Публичная регистрация — только после правовой проверки

Сначала пройди `LEGAL_REVIEW_CHECKLIST.md` с профильным юристом. Затем:

1. Заполни `public/privacy.html`, `public/consent.html`, `public/terms.html` фактическими реквизитами и процессами.
2. Удали все шаблонные поля и черновые предупреждения, только если документы действительно проверены и готовы.
3. Укажи реальные версии документов и реквизиты оператора в `.env`.
4. Рассчитай контрольную сумму опубликованного согласия:

```bash
sha256sum public/consent.html
```

5. Запиши результат в `LEGAL_CONSENT_SHA256`.
6. Только после подтверждения юриста и выполнения уведомлений/процедур по применимому праву выставь `APP_LEGAL_LAUNCH_APPROVED=true` и `APP_REGISTRATION_ENABLED=true`.
7. Перезапусти backend:

```bash
docker compose up -d --build backend
```

Сервер дополнительно блокирует регистрацию, пока версии документов не финальные, шаблонные поля не убраны и hash согласия не совпадает. Это только fail-closed техническая проверка. Она не определяет, что документы юридически корректны, что уведомление подано или что трансграничной передачи нет.

## 7. Java Runner

`RUNNER_ENABLED=false` — обязательное значение до отдельного проекта защиты. Не подключай публичный Judge0 или другую зарубежную площадку. Запускаемый пользователем код должен выполняться в отдельной изолированной среде в РФ, не имеющей доступа к PostgreSQL и backend secrets, с ограничением CPU, RAM, процессов, времени и сети. Согласуй роль и договор с владельцем runner-хоста; учитывай, что исходный код пользователя тоже может содержать персональные данные.

## 8. Обновление

Перед обновлением:

1. Сделай резервную копию БД.
2. Проверь миграции Flyway на копии.
3. Обнови код через `git pull`.
4. Выполни `docker compose up -d --build`.
5. Проверь `/api/health`, `/api/meta/public`, вход/выход и синхронизацию на тестовом аккаунте.
6. Проверь восстановление backup и отсутствие данных в логах.

## Ограничения этой версии

- Backend подготовлен под Spring Boot 4.1.2 и Java 21; локально в контейнере разработки Maven/Docker не установлены, поэтому сборку необходимо выполнить на VPS/CI перед запуском.
- Восстановление пароля — по одноразовому recovery code, который показывается один раз. Нет email/SMS. Потеря recovery code может означать потерю доступа.
- Сессии хранятся в одном процессе. Перезапуск завершит пользовательские сессии.
- Rate limiter в памяти одного backend-процесса ограничивает частоту попыток, но перед массовым открытием нужен дополнительный лимит на reverse proxy/WAF.
- Регистрация и runner по умолчанию выключены.
